# Idiomas y moneda

El template incluye dos idiomas de interfaz, inglés (predeterminado) y español, y USD como moneda predeterminada. Las páginas viven bajo un prefijo de idioma (`/en/...`, `/es/...`). Todo lo que sigue se contrastó con el código de `src/i18n`, `src/proxy.ts`, `src/app/[lang]`, `scripts/lib/configure.ts` y las pruebas citadas en cada sección. [English](i18n.md).

| Ajuste | Dónde | Valor incluido |
| --- | --- | --- |
| Idiomas ofrecidos, el predeterminado primero | `i18n.locales`, `i18n.defaultLocale` en `src/template.config.ts` | `en`, `es`; predeterminado `en` |
| Moneda predeterminada | `currency` | `USD` |
| Monedas ofrecidas en el editor de productos | `currencies` | `USD, EUR, GBP, MXN, ARS, BRL, PYG` |
| Eslogan | `description`: un texto, o uno por idioma | mapa por idioma (`en`, `es`) |
| Idiomas registrados (código, nombre nativo, etiqueta `Intl`) | `LOCALE_DEFINITIONS` en `src/i18n/config.ts` | `en` / English / `en-US`, `es` / Español / `es-PY` |

Son ajustes de la instalación, no variables de entorno, de modo que todas las réplicas y todas las versiones sirven los mismos idiomas y la misma moneda. Se compilan dentro de la imagen; cambiarlos es un cambio de código que se publica como imagen inmutable nueva ([producción](production.md)). Los validadores se ejecutan cuando se importa `src/i18n/runtime.ts`, no en cada solicitud. `npm run doctor` y `npm test` ejecutan las mismas comprobaciones antes de publicar, así que conviene correrlos en CI.

Se cambian con la CLI, que usa los mismos validadores y reescribe `src/template.config.ts` (el objeto debe seguir siendo JSON simple; la CLI rechaza un archivo que no puede interpretar):

```sh
npm run configure -- --help
npm run configure -- --currency EUR --currencies EUR,USD,GBP
npm run configure -- --locale en --locales en,es
npm run doctor      # informa i18n.settings y currency.settings
```

`npm run doctor` también revisa la base de datos y la autenticación; en una base sin migraciones esas comprobaciones fallan, mientras `i18n.settings` y `currency.settings` siguen informando.

## 1. Enrutamiento

Todas las páginas están en `src/app/[lang]/`. `src/app/[lang]/layout.tsx` es el layout raíz: genera `<html lang>`, define `dynamicParams = false`, lista los idiomas habilitados en `generateStaticParams` y llama a `notFound()` para cualquier otro valor. No existe `src/app/layout.tsx`. Páginas: tienda (`/`), `cart`, `checkout/return`, `admin`, `sign-in`, `onboarding`, `onboarding/connections`, `consent`, además de los límites `error` y `not-found` y un `loading.tsx` por grupo de páginas (`admin`, `cart`, `checkout`, `consent`, `onboarding`, `sign-in`), cada uno reexporta `src/components/route-loading.tsx`. Una ruta comodín (`src/app/[lang]/[...rest]/page.tsx`) llama a `notFound()` para cualquier otra ruta bajo un prefijo válido, de modo que una URL desconocida responde HTTP 404 con la página traducida de «no encontrado» y no la predeterminada en inglés del framework. A propósito no hay un `loading.tsx` en `src/app/[lang]/`: ese límite envolvería la ruta comodín, la respuesta empezaría a transmitirse con estado 200 antes de que se ejecute `notFound()` y toda URL desconocida sería un «soft 404» (ver la sección «Status codes» de `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md`). Los `loading.tsx` nuevos van dentro de las rutas de página, nunca en `[lang]`.

`src/proxy.ts` es la convención de archivo `proxy` de Next.js 16 (el antiguo middleware; ver `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`). Para una solicitud cuya ruta no tiene un prefijo de idioma habilitado, elige un idioma y redirige:

1. Si el prefijo ya está presente (`/en`, `/es/cart`): no hace nada; la solicitud continúa.
2. Si no, la cookie `NEXT_LOCALE`, siempre que su valor sea un idioma habilitado.
3. Si no, la cabecera `Accept-Language`: etiquetas ordenadas por `q`, se ignoran los comodines y `q=0`; primero la etiqueta exacta y después el mismo idioma (`es-AR` coincide con `es`). Se ignora la cabecera si supera 1024 caracteres y solo se leen las primeras 20 etiquetas.
4. Si no, `i18n.defaultLocale`.

La redirección es `307`, a la misma ruta con el prefijo añadido y la **cadena de consulta conservada**: cada nombre y valor de parámetro llega sin cambios (`/consent?client_id=…&sig=…` pasa a `/es/consent?client_id=…&sig=…`). Next.js vuelve a escribir la cabecera `Location`, así que el texto crudo puede diferir (`%20` pasa a `+` y los nombres repetidos se agrupan); el proveedor OAuth verifica su firma sobre los parámetros decodificados y canonicalizados, por lo que no le afecta. Las barras iniciales de la ruta se colapsan para que `//host` nunca llegue a ser un destino de redirección relativo al protocolo. Un prefijo que no es un idioma habilitado (`/fr/cart`) es una ruta común y pasa a `/en/fr/cart`, que no coincide con ninguna página y termina en la página traducida de «no encontrado». La lógica está en funciones puras de `src/i18n/negotiate.ts` y `src/i18n/routing.ts`; `tests/i18n-routing.test.ts` la cubre.

El proxy nunca escribe la cookie. Solo lo hace el selector de idioma (`src/i18n/switcher.tsx`): `NEXT_LOCALE=<código>; Path=/; Max-Age=31536000; SameSite=Lax`, más `Secure` en HTTPS. La escribe un script, por lo que no es `HttpOnly`; contiene solo un código de idioma. Luego el selector navega por completo a la misma página (conservando consulta y fragmento) en el idioma elegido, de modo que `<html lang>` y todos los espacios de nombres cambian juntos. No muestra nada cuando la instalación ofrece un solo idioma; las URL conservan igualmente el prefijo.

### Qué omite el proxy y por qué

El matcher es `/((?!api(?:/|$)|_next/|\.well-known/|.*\..*).*)`:

| Omitido | Motivo |
| --- | --- |
| `/api/...` | API HTTP, Better Auth, MCP (`/api/mcp`), webhooks de pago, `/api/health`, `/api/readiness`. Clientes, agentes y sondas necesitan URL estables sin prefijo y respuestas que no dependan del idioma del visitante. |
| `/_next/...` | Activos del framework. |
| `/.well-known/...` | Descubrimiento OAuth. Debe responder directamente y nunca redirigir ([MCP](mcp.md)). |
| Cualquier ruta con un punto | Archivos estáticos de `public/` como `/demo/tee.svg` o `/favicon.ico`. |

Las URL de página sin prefijo siguen funcionando como puntos de entrada. `src/lib/auth.ts` fija `loginPage` en `/sign-in`, `consentPage` en `/consent` y `postLogin.page` en `/onboarding`, y `src/payments/server.ts` construye las URL de retorno de Stripe como `/checkout/return?from=success|cancel`. Todas pasan por el proxy y llegan a `/<idioma>/...` con su consulta intacta. El idioma es el del navegador, según el orden anterior; el recorrido OAuth no transporta uno.

### Caché y CDN

La redirección lleva `Vary: Accept-Language, Cookie` y `Cache-Control: private, no-store`, porque su destino depende del visitante. Conservar esas cabeceras.

- No almacenar la redirección en una caché compartida. Una redirección guardada para `/` enviaría a todos los visitantes al idioma del primero.
- Reenviar `Cookie` y `Accept-Language` al origen para las URL de página sin prefijo. Si el borde las elimina, todos esos visitantes reciben el idioma predeterminado.
- No añadir una regla en el borde que anteponga un idioma a `/api/*`, `/_next/*` o `/.well-known/*`.
- Las páginas con prefijo son URL por idioma. Si se almacenan en caché lo decide [producción](production.md) (sin caché pública de HTML autenticado).

## 2. Catálogos de mensajes

El texto vive en `src/i18n/messages/<idioma>/<espacio>.json`, un archivo por área funcional, los mismos siete archivos para cada idioma (`NAMESPACES` en `src/i18n/config.ts`):

| Espacio de nombres | Contenido | Quién lo carga |
| --- | --- | --- |
| `common` | Cabecera, pie, límites de error, selector de idioma, título de página | Layout raíz `src/app/[lang]/layout.tsx` (todas las páginas) |
| `errors` | `generic`, `reference`, `codes.<CÓDIGO>` | Layout raíz |
| `runtime` | Aviso y formulario de ajustes operativos | Layout raíz |
| `storefront` | Inicio y colección de productos | `src/app/[lang]/page.tsx` mediante `I18nScope` |
| `cart` | Carrito, pago, retorno del pago | Layouts de `cart` y `checkout` mediante `I18nScope` |
| `admin` | Administración | Layout de `admin` mediante `I18nScope` |
| `auth` | Inicio de sesión, onboarding, conexiones, consentimiento, etiquetas de scopes | Layouts de `sign-in`, `onboarding` y `consent` mediante `I18nScope` |

El servidor carga los espacios que una página necesita (`loadMessages` en `src/i18n/messages.ts`) y los entrega a `I18nProvider`; el navegador recibe solo esos, no todos los catálogos. Los proveedores se anidan y se combinan, de modo que el layout de una ruta suma su espacio al del layout raíz. En un idioma que no es el predeterminado, cada clave ausente recurre al texto del idioma predeterminado, así que una laguna muestra inglés en lugar de una clave cruda. Es una red de seguridad: las pruebas de paridad descritas abajo fallan ante cualquier laguna.

`src/i18n/translate.ts` tipa las claves a partir de los archivos en inglés (`Messages`), por lo que, con `const t = useT("cart")`, llamar a `t("missing")` es un error de TypeScript. Una clave que no existe en ningún idioma se muestra como la propia clave. Para añadir un espacio de nombres: crear `<espacio>.json` en la carpeta de cada idioma, añadir el nombre a `NAMESPACES` en `src/i18n/config.ts` y a `Messages` en `src/i18n/translate.ts`, y cargarlo desde un layout.

### Convenciones de claves y texto

- Objetos anidados, camelCase, agrupados por pantalla o función (`cart.summary.title`). Una clave no puede contener un punto; las pruebas lo rechazan.
- Los marcadores son `{nombre}`. Cada idioma debe usar exactamente los mismos marcadores que el inglés para una clave. Un marcador desconocido queda visible como `{nombre}`.
- Sin HTML ni marcado en los mensajes. Dividir una frase alrededor de un enlace o de texto en negrita en claves separadas.
- No armar frases con fragmentos en el código. El orden de las palabras y la gramática cambian según el idioma: dar a cada frase una sola clave con marcadores.
- Los archivos `en` deben estar en inglés (las pruebas rechazan letras del español en `en`).
- El nombre de marca y otros datos son valores, no texto: pasarlos como marcadores (`{brand}`).

### Plurales

Un mensaje plural es un objeto con categorías CLDR: `zero`, `one`, `two`, `few`, `many`, `other`. `other` es obligatoria. Intl elige la categoría con el valor de `count` (`new Intl.PluralRules(formatLocale)`), así que pasar `count` como **número sin formato**: `t("itemCount", { count: 3 })`. Un texto ya formateado como `"1,234"` se lee como no numérico y cae en `other`. Usar otro marcador para el texto visible.

El conjunto requerido depende del idioma y `tests/i18n-messages.test.ts` lo exige con `Intl.PluralRules(formatLocale).resolvedOptions().pluralCategories`:

| Idioma | Categorías requeridas |
| --- | --- |
| Inglés (`en-US`) | `one`, `other` |
| Español (`es-PY`) | `one`, `many`, `other` |

El español necesita `many` porque CLDR lo usa para los múltiplos exactos de un millón (`select(1000000)` devuelve `many`), donde el sustantivo lleva «de»: `"{count} artículo"` (one), `"{count} de artículos"` (many), `"{count} artículos"` (other), como en `cart.json`. Sin ella el tiempo de ejecución usaría `other` en silencio y mostraría «1000000 artículos»; la prueba convierte esa omisión en un fallo. Antes de traducir a otro idioma, listar sus categorías:

```sh
node -e "console.log(new Intl.PluralRules('ru').resolvedOptions().pluralCategories)"
```

## 3. Escribir texto de interfaz

Los Client Components importan de `src/i18n/provider.tsx` y `src/i18n/link.tsx`. Los Server Components usan `getTranslator` (`src/i18n/messages.ts`) y `lang()` de `next/root-params`.

| Necesidad | Usar |
| --- | --- |
| Texto | `const t = useT("cart"); t("summary.title", { count })` |
| Dinero, números, fechas | `const { money, number, dateTime } = useFormat(); money(priceMinor, product.currency)` |
| Enlace interno | `<LocaleLink href="/cart">` (solo acepta rutas internas simples) |
| Ruta desde código | `const localePath = useLocalePath(); window.location.assign(localePath("/sign-in"))`; conserva consulta y fragmento y no toca URL externas |
| Idioma activo | `useLocale()` |
| Solicitud fallida | `const errorMessage = useErrorMessage(); errorMessage(error, t("saveFailed"))` |
| Texto de servidor, metadatos | `const t = await getTranslator(locale, "common")` |
| Ruta nueva que necesita un espacio | `<I18nScope namespaces={["cart"]}>` en el `layout.tsx` de la ruta |
| Selector de idioma | `<LocaleSwitcher />` |

Reglas: ningún texto visible literal en un componente; ningún `href` fijo como `/en/...` o `/cart` en la interfaz; ningún formato de dinero a mano. Si una constante aparece en el código y en un mensaje, mantenerlas sincronizadas y decirlo en un comentario (ver `PASSWORD_MIN_LENGTH` en `sign-in/page.tsx`). Ninguna prueba unitaria detecta un texto literal olvidado en un componente ni un `href` fijo: las pruebas de paridad solo comparan catálogos. Abrir las pantallas modificadas en ambos idiomas.

## 4. El servidor habla inglés y los errores llevan código

Las respuestas de la API, la salida y descripciones de MCP, los registros, la telemetría y la auditoría están en inglés y no se localizan. Los fallos llevan un código estable. `route()` en `src/lib/http.ts` responde `{ "error": { "code", "message" }, "requestId" }`; `src/lib/api-client.ts` lo convierte en un `ApiError` con `code`. El navegador muestra el texto elegido por código:

1. `useErrorMessage()` busca `errors.codes.<CÓDIGO>` en el idioma activo.
2. Un código desconocido usa el texto alternativo traducido del llamador y, si no hay, `errors.generic`.
3. Si la respuesta traía un ID de solicitud, se añade `errors.reference` («Referencia: {id}»).

Los errores de flujo originados en el navegador siguen la misma idea: `CheckoutAttemptError` en `src/components/checkout-attempt.ts` tiene códigos que se asocian con claves `failures.*` de `cart.json`.

`tests/error-codes.test.ts` hace cumplir la política:

- Recorre `src/` en busca de `new AppError('CÓDIGO', …)`, respuestas `code: 'CÓDIGO'` y códigos de `ApiError` del cliente, y falla si a `errors.codes` en `en` o `es` le falta alguno, indicando archivo y línea del primer uso.
- Los `errors.json` de `en` y `es` deben coincidir clave por clave y marcador por marcador, y ningún mensaje puede estar vacío.
- Los archivos de servidor (`src/app/api`, `src/core`, `src/payments`, `src/extensions`, `src/lib/*.ts` y los archivos `service`, `contracts` y `server` del runtime) no pueden contener tildes del español, signos de apertura, voseo ni las etiquetas antiguas en español.
- El sobre HTTP: los fallos de dominio conservan mensaje en inglés y código, los de validación devuelven `INVALID_INPUT` sin repetir lo enviado y los inesperados devuelven `INTERNAL_ERROR` sin filtrar la causa.

Para añadir un código: lanzar `new AppError('MI_CODIGO', 'English sentence.', status)`, añadir `codes.MI_CODIGO` a `errors.json` en `en` y `es`, y ejecutar `npx vitest run tests/error-codes.test.ts`.

## 5. Añadir un idioma

Ejemplo: francés (`fr`). Sustituir el código y los nombres por los propios.

1. Copiar los catálogos en inglés y traducir solo los valores; conservar claves y `{marcadores}`:
   ```sh
   cp -r src/i18n/messages/en src/i18n/messages/fr
   ```
2. Consultar las categorías plurales del idioma (sección 2) y dar a cada objeto plural al menos esas formas, siempre con `other`. La prueba falla si falta una categoría; no rechaza una de más.
3. Registrarlo en `LOCALE_DEFINITIONS` de `src/i18n/config.ts`:
   ```ts
   { code: 'fr', nativeName: 'Français', formatLocale: 'fr-FR' },
   ```
   `code` es el prefijo de URL, el valor de la cookie, el nombre de la carpeta y `<html lang>`. Los códigos incluidos son subetiquetas primarias (`en`, `es`) y una preferencia del navegador como `fr-CA` sigue coincidiendo con `fr`; la región va en `formatLocale`. `nativeName` es lo que muestra el selector.
4. Habilitarlo. Sin este paso queda registrado pero no se ofrece:
   ```sh
   npm run configure -- --locales en,es,fr
   ```
   Un código no registrado falla y muestra la lista de idiomas registrados.
5. Opcionalmente, añadir un eslogan. `description` puede ser un mapa por idioma; un idioma sin entrada recurre al idioma predeterminado. `--description` solo reemplaza la entrada del idioma predeterminado, así que para los demás se edita el mapa en `src/template.config.ts`.
6. Ejecutar `npm test`. `tests/i18n-messages.test.ts` falla con una línea por problema: carpeta o archivo de espacio ausente, clave ausente o sobrante, marcador cambiado, plural donde el inglés tiene texto simple, categorías plurales faltantes, texto vacío, marcado, llaves sueltas y un idioma usado en `template.config.ts` que no está registrado. `tests/i18n-translate.test.ts` y `tests/configure.test.ts` cubren el traductor y la CLI.
7. `tests/error-codes.test.ts` importa `en` y `es` de forma explícita. Añadir allí también el `errors.json` nuevo para que sus códigos reciban las mismas comprobaciones (la prueba de paridad ya compara sus claves con el inglés).
8. Revisar el idioma en el navegador: URL sin prefijo con ese `Accept-Language`, el selector, el carrito, la administración, el inicio de sesión y el consentimiento. Las pruebas automáticas cubren catálogos y lógica de rutas, no la calidad de la traducción ni la maquetación.

No publicar un idioma copiando el inglés a la carpeta nueva y dejándolo así: las pruebas pasan, pero la página no queda traducida.

## 6. Qué no se localiza

- **Datos del catálogo.** Nombres, descripciones y categorías de producto se guardan una vez, como los escribió el comerciante, y se muestran así en todos los idiomas. El catálogo de demostración está en inglés.
- **Nombre de marca.** Un solo texto, `name`. Solo el eslogan (`description`) puede variar por idioma.
- **Avisos.** El aviso que escribe un comerciante en los ajustes operativos se muestra tal cual en todos los idiomas ([ajustes operativos](runtime-settings.md)).
- **Correo.** El template no envía ninguno. Cualquier correo que se añada necesita su propia localización.
- **Stripe.** La línea de Checkout alojado es el texto fijo en inglés `Store order` (`src/payments/providers/stripe.ts`). El adaptador no pasa `locale` a Stripe, así que el idioma de la página alojada lo decide Stripe y aquí no se ha probado.
- **Texto de servidor.** Mensajes de API, MCP, registros, telemetría y auditoría (sección 4).
- **Derecha a izquierda.** El layout raíz no emite el atributo `dir` y la hoja de estilos no se revisó para espejado. Añadir árabe o hebreo exige antes una revisión de CSS.
- **SEO.** No se genera `hreflang`, mapa del sitio ni `robots`. El título de la página sale de `common.meta.title` y la meta descripción del ajuste `description`, ambos por idioma.

## 7. Moneda

`currency` es la predeterminada (incluida: `USD`); `currencies` es la lista que ofrece el editor de productos y debe incluirla. Cada código debe ser un código ISO 4217 en mayúsculas que `Intl.supportedValuesOf('currency')` conozca en el Node en ejecución; la lista tiene de 1 a 30 códigos sin repetir.

```sh
npm run configure -- --currency EUR --currencies EUR,USD,GBP
npm run doctor
```

Sin `--currencies` se conserva la lista actual y la moneda nueva se añade al inicio si falta. También se pueden editar `currency` y `currencies` directamente en `src/template.config.ts`; la aplicación y `npm run doctor` aplican la misma validación. Recompilar o reiniciar para aplicarlo.

### Qué cambia

- La moneda preseleccionada para un **producto nuevo** en el editor y el orden de su lista (primero la predeterminada).
- La moneda de los **totales vacíos**: la tarjeta de ingresos del panel antes de la primera venta y la moneda de respaldo del carrito cuando no tiene productos.
- La moneda que se muestra como predeterminada en el panel de ajustes de la administración.
- El catálogo de demostración: `npm run demo:setup` usa `templateConfig.currency`.

### Qué no cambia

- **Precios existentes.** No se convierte nada. Cada producto conserva su `priceMinor` y su `currency`; la CLI imprime ese aviso en cada ejecución. Si los importes deben cambiar, hay que reajustar o recrear los productos.
- **Moneda por producto.** Cada producto tiene su propia moneda. Un producto cuya moneda ya no está en la lista la conserva y el editor sigue mostrándola. La lista solo limita el desplegable del editor: el dominio, la API HTTP y las herramientas MCP aceptan cualquier grupo de tres letras mayúsculas como moneda de producto (`currency()` en `src/core/service.ts`), de modo que no es una lista permitida en el servidor.
- **Monedas mezcladas.** Un pedido debe usar una sola moneda. El dominio rechaza la mezcla con `MIXED_CURRENCY` (422) y el carrito la detecta antes de enviar. Un catálogo en varias monedas no se puede comprar en un único carrito.
- **Stripe.** Ofrecer una moneda no la hace cobrable. El adaptador de Checkout alojado acepta solo los códigos de `STRIPE_CURRENCY_EXPONENTS` cuyo exponente coincida con `Intl` y rechaza el resto con `PAYMENT_CURRENCY_UNSUPPORTED` antes de reservar stock ([pagos](payments.md)). Los pedidos manuales no tienen ese límite.

### Unidades menores

El dinero es un entero en la unidad menor de la moneda. El factor sale de `Intl` (`currencyFactor` en `src/i18n/format.ts`): `USD` 100, `PYG` y `JPY` 1, `KWD` 1000. El editor convierte lo que escribe la persona con `Math.round(precio * factor)`; la visualización divide por el mismo factor. Los precios siempre se resuelven en el servidor; el total del navegador es solo una confirmación.

La siembra de demostración (`demoCatalog` en `src/db/seed.ts`) escribe los precios como números en unidades mayores y los multiplica por el factor: `USD` 29 es 2900 y `KWD` 29 es 29000. En monedas sin decimales los mismos números pasan a ser importes pequeños (29 `JPY`, decimales redondeados): la demostración muestra el mecanismo, no es una lista de precios realista. `tests/seed-currency.test.ts` cubre `EUR`, `GBP`, `JPY` y `KWD`. `seedDemo` nunca reescribe un producto existente, así que un `demo.db` antiguo conserva sus nombres y su moneda; `demo:setup` lo advierte y la solución es borrar `demo.db` y volver a ejecutar.

### Formato por idioma

`formatMoney`, `formatNumber` y `formatDateTime` usan el `formatLocale` del idioma, de modo que un mismo precio se formatea distinto según el idioma. Salida de ejemplo con Node 22 y sus datos ICU incluidos (los navegadores pueden diferir un poco):

| Importe | `en-US` | `es-PY` |
| --- | --- | --- |
| 2900 USD | `$29.00` | `USD 29,00` |
| 123450 EUR | `€1,234.50` | `EUR 1.234,50` |
| 32000 PYG | `PYG 32,000` | `Gs. 32.000` |

Cambiar de idioma nunca convierte ni reajusta nada.

## 8. Verificar

```sh
npx vitest run tests/i18n-messages.test.ts tests/i18n-routing.test.ts tests/i18n-translate.test.ts tests/error-codes.test.ts tests/configure.test.ts tests/seed-currency.test.ts
```
