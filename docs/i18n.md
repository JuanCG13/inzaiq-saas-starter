# Languages and currency

The template ships two interface languages, English (default) and Spanish, and USD as the default currency. Pages live under a language prefix (`/en/...`, `/es/...`). Everything below was checked against the code in `src/i18n`, `src/proxy.ts`, `src/app/[lang]`, `scripts/lib/configure.ts` and the tests named in each section. [Español](i18n.es.md).

| Setting | Where | Shipped value |
| --- | --- | --- |
| Languages offered, default first | `i18n.locales`, `i18n.defaultLocale` in `src/template.config.ts` | `en`, `es`; default `en` |
| Default currency | `currency` | `USD` |
| Currencies offered in the product editor | `currencies` | `USD, EUR, GBP, MXN, ARS, BRL, PYG` |
| Tagline | `description`: one string, or one per language | per-language map (`en`, `es`) |
| Registered languages (code, native name, `Intl` tag) | `LOCALE_DEFINITIONS` in `src/i18n/config.ts` | `en` / English / `en-US`, `es` / Español / `es-PY` |

These are installation settings, not environment variables, so every replica and every release serves the same languages and currency. They are compiled into the image; changing them is a code change that ships as a new immutable image ([production](production.md)). The validators run when `src/i18n/runtime.ts` is imported, not per request. `npm run doctor` and `npm test` run the same checks before you ship, so run them in CI.

Change them with the CLI, which uses the same validators and rewrites `src/template.config.ts` (keep the object plain JSON; the CLI refuses a file it cannot parse):

```sh
npm run configure -- --help
npm run configure -- --currency EUR --currencies EUR,USD,GBP
npm run configure -- --locale en --locales en,es
npm run doctor      # reports i18n.settings and currency.settings
```

`npm run doctor` also checks the database and auth; on a database without migrations those checks fail while `i18n.settings` and `currency.settings` still report.

## 1. Routing

Every page is under `src/app/[lang]/`. `src/app/[lang]/layout.tsx` is the root layout: it renders `<html lang>`, sets `dynamicParams = false`, lists the enabled languages in `generateStaticParams`, and calls `notFound()` for any other value. There is no `src/app/layout.tsx`. Pages: storefront (`/`), `cart`, `checkout/return`, `admin`, `sign-in`, `onboarding`, `onboarding/connections`, `consent`, plus the `error` and `not-found` boundaries and one `loading.tsx` per page group (`admin`, `cart`, `checkout`, `consent`, `onboarding`, `sign-in`), each re-exporting `src/components/route-loading.tsx`. A catch-all (`src/app/[lang]/[...rest]/page.tsx`) calls `notFound()` for any other path under a valid prefix, so an unknown URL answers HTTP 404 with the translated not-found page instead of the framework's English default. There is deliberately no `loading.tsx` at `src/app/[lang]/`: that boundary would wrap the catch-all, the response would start streaming with status 200 before `notFound()` runs, and every unknown URL would be a soft 404 (see the "Status codes" section of `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md`). Add new `loading.tsx` files inside the page routes, never at `[lang]`.

`src/proxy.ts` is the Next.js 16 `proxy` file convention (the former middleware; see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`). For a request whose path has no enabled language prefix it chooses a language and redirects:

1. A prefix already present (`/en`, `/es/cart`): nothing happens; the request continues.
2. Otherwise the `NEXT_LOCALE` cookie, if its value is an enabled language.
3. Otherwise the `Accept-Language` header: tags ordered by `q`, wildcards and `q=0` ignored, exact tag first and then the same language (`es-AR` matches `es`). The header is ignored above 1024 characters and only the first 20 tags are read.
4. Otherwise `i18n.defaultLocale`.

The redirect is `307`, to the same path with the prefix added and the **query string kept**: every parameter name and value arrives unchanged (`/consent?client_id=…&sig=…` becomes `/es/consent?client_id=…&sig=…`). Next.js writes the `Location` header again, so the raw text can differ (`%20` becomes `+`, repeated names are grouped); the OAuth provider verifies its signature over the decoded, canonicalized parameters, so this does not affect it. Leading slashes in the path are collapsed so `//host` can never become a protocol-relative redirect target. A prefix that is not an enabled language (`/fr/cart`) is an ordinary path and becomes `/en/fr/cart`, which matches no page and ends in the translated not-found page. Pure functions in `src/i18n/negotiate.ts` and `src/i18n/routing.ts` hold this logic; `tests/i18n-routing.test.ts` covers it.

The proxy never sets the cookie. Only the language selector (`src/i18n/switcher.tsx`) does: `NEXT_LOCALE=<code>; Path=/; Max-Age=31536000; SameSite=Lax`, plus `Secure` on HTTPS. It is written by script, so it is not `HttpOnly`; it holds only a language code. The selector then does a full navigation to the same page (query and hash kept) in the chosen language, so `<html lang>` and every message namespace change together. It renders nothing when the installation offers one language; URLs still carry the prefix.

### What the proxy skips, and why

The matcher is `/((?!api(?:/|$)|_next/|\.well-known/|.*\..*).*)`:

| Skipped | Reason |
| --- | --- |
| `/api/...` | HTTP API, Better Auth, MCP (`/api/mcp`), payment webhooks, `/api/health`, `/api/readiness`. Clients, agents and probes need stable unprefixed URLs and responses that do not depend on the visitor's language. |
| `/_next/...` | Framework assets. |
| `/.well-known/...` | OAuth discovery. It must answer directly and never redirect ([MCP](mcp.md)). |
| Any path containing a dot | Static files from `public/` such as `/demo/tee.svg` or `/favicon.ico`. |

Unprefixed page URLs keep working as entry points. `src/lib/auth.ts` sets the OAuth `loginPage` to `/sign-in`, `consentPage` to `/consent` and `postLogin.page` to `/onboarding`, and `src/payments/server.ts` builds Stripe return URLs as `/checkout/return?from=success|cancel`. All of them pass through the proxy and land on `/<language>/...` with their query intact. The language is the browser's, as above; the OAuth round trip does not carry one.

### Caching and CDN

The redirect carries `Vary: Accept-Language, Cookie` and `Cache-Control: private, no-store`, because its destination depends on the visitor. Keep those headers.

- Do not cache the redirect in a shared cache. A stored redirect for `/` would send every visitor to the first visitor's language.
- Forward `Cookie` and `Accept-Language` to the origin for unprefixed page URLs. If the edge strips them, every such visitor gets the default language.
- Do not add an edge rule that prefixes a language on `/api/*`, `/_next/*` or `/.well-known/*`.
- Prefixed pages are per-language URLs. Whether to cache them is the decision in [production](production.md) (no public cache of authenticated HTML).

## 2. Message catalogs

Text lives in `src/i18n/messages/<language>/<namespace>.json`, one file per feature area, the same seven files for every language (`NAMESPACES` in `src/i18n/config.ts`):

| Namespace | Content | Loaded by |
| --- | --- | --- |
| `common` | Header, footer, boundaries, language selector, page title | Root layout `src/app/[lang]/layout.tsx` (every page) |
| `errors` | `generic`, `reference`, `codes.<CODE>` | Root layout |
| `runtime` | Notice and runtime settings form | Root layout |
| `storefront` | Home and product collection | `src/app/[lang]/page.tsx` through `I18nScope` |
| `cart` | Cart, checkout, payment return | Layouts of `cart` and `checkout` through `I18nScope` |
| `admin` | Admin workspace | Layout of `admin` through `I18nScope` |
| `auth` | Sign-in, onboarding, connections, consent, scope labels | Layouts of `sign-in`, `onboarding` and `consent` through `I18nScope` |

The server loads the namespaces a page needs (`loadMessages` in `src/i18n/messages.ts`) and passes them to `I18nProvider`; the browser receives only those, not every catalog. Providers nest and merge, so a route layout adds its namespace to the root layout's. In a non-default language each key falls back to the default language's text, so a gap shows English instead of a raw key. That fallback is a safety net: the parity tests below fail on any gap.

`src/i18n/translate.ts` types the keys from the English files (`Messages`), so with `const t = useT("cart")`, calling `t("missing")` is a TypeScript error. A key that exists nowhere renders as the key itself. To add a namespace: create `<namespace>.json` in every language folder, add the name to `NAMESPACES` in `src/i18n/config.ts` and to `Messages` in `src/i18n/translate.ts`, and load it from a layout.

### Key and text conventions

- Nested objects, camelCase, grouped by screen or feature (`cart.summary.title`). A key must not contain a dot; the tests reject it.
- Placeholders are `{name}`. Every language must use exactly the same placeholders as English for a key. An unknown placeholder stays visible as `{name}`.
- No HTML or markup in messages. Split a sentence around a link or bold text into separate keys.
- Do not assemble sentences from fragments in code. Word order and grammar differ by language, so give each sentence one key with placeholders.
- English files must be English (the tests reject Spanish letters in `en`).
- Brand name and other data are values, not text: pass them as placeholders (`{brand}`).

### Plurals

A plural message is an object keyed by CLDR categories: `zero`, `one`, `two`, `few`, `many`, `other`. `other` is mandatory. Intl selects the category from the `count` value (`new Intl.PluralRules(formatLocale)`), so pass `count` as a **raw number**: `t("itemCount", { count: 3 })`. A pre-formatted string such as `"1,234"` reads as not-a-number and falls to `other`. Use another placeholder for the display text.

The required set comes from the language, and `tests/i18n-messages.test.ts` enforces it from `Intl.PluralRules(formatLocale).resolvedOptions().pluralCategories`:

| Language | Categories required |
| --- | --- |
| English (`en-US`) | `one`, `other` |
| Spanish (`es-PY`) | `one`, `many`, `other` |

Spanish needs `many` because CLDR uses it for exact multiples of one million (`select(1000000)` is `many`), where the noun takes "de": `"{count} artículo"` (one), `"{count} de artículos"` (many), `"{count} artículos"` (other), as in `cart.json`. Without it the runtime would silently use `other` and print "1000000 artículos"; the test makes the omission a failure instead. List the categories for any other language before translating:

```sh
node -e "console.log(new Intl.PluralRules('ru').resolvedOptions().pluralCategories)"
```

## 3. Writing UI text

Client Components import from `src/i18n/provider.tsx` and `src/i18n/link.tsx`. Server Components use `getTranslator` (`src/i18n/messages.ts`) and `lang()` from `next/root-params`.

| Need | Use |
| --- | --- |
| Text | `const t = useT("cart"); t("summary.title", { count })` |
| Money, numbers, dates | `const { money, number, dateTime } = useFormat(); money(priceMinor, product.currency)` |
| Internal link | `<LocaleLink href="/cart">` (accepts plain internal paths only) |
| Path for code | `const localePath = useLocalePath(); window.location.assign(localePath("/sign-in"))`; keeps query and hash, leaves external URLs alone |
| Active language | `useLocale()` |
| Failed request | `const errorMessage = useErrorMessage(); errorMessage(error, t("saveFailed"))` |
| Server text, metadata | `const t = await getTranslator(locale, "common")` |
| New route needing a namespace | `<I18nScope namespaces={["cart"]}>` in the route's `layout.tsx` |
| Language selector | `<LocaleSwitcher />` |

Rules: no literal user-facing string in a component; no hard-coded `/en/...` or `/cart` href in the UI; no money formatting by hand. Keep a constant that appears both in code and in a message in sync and say so in a comment (see `PASSWORD_MIN_LENGTH` in `sign-in/page.tsx`). No unit test detects a literal string left in a component or a hard-coded href: the parity tests only compare catalogs. Open the changed screens in both languages.

## 4. Server text is English, errors carry codes

API responses, MCP tool output and descriptions, logs, telemetry and audit text are English and are not localized. Failures carry a stable code. `route()` in `src/lib/http.ts` answers `{ "error": { "code", "message" }, "requestId" }`; `src/lib/api-client.ts` turns that into an `ApiError` with `code`. The browser shows text chosen by code:

1. `useErrorMessage()` looks up `errors.codes.<CODE>` in the active language.
2. An unknown code uses the caller's translated fallback, else `errors.generic`.
3. When the response had a request ID, `errors.reference` ("Reference: {id}") is appended.

Flow errors raised in the browser use the same idea: `CheckoutAttemptError` in `src/components/checkout-attempt.ts` has codes mapped to `cart.json` `failures.*` keys.

`tests/error-codes.test.ts` enforces the policy:

- It scans `src/` for `new AppError('CODE', …)`, `code: 'CODE'` responses and client `ApiError` codes, and fails if `errors.codes` in `en` or `es` lacks one, naming the file and line of the first use.
- `en` and `es` `errors.json` must match key by key and placeholder by placeholder, and no message may be empty.
- Server files (`src/app/api`, `src/core`, `src/payments`, `src/extensions`, `src/lib/*.ts` and the runtime `service`, `contracts` and `server` files) must not contain Spanish accents, inverted punctuation, voseo or the old Spanish labels.
- The HTTP envelope: domain failures keep their English message and code, validation failures return `INVALID_INPUT` without echoing input, unexpected failures return `INTERNAL_ERROR` without leaking the cause.

To add a code: throw `new AppError('MY_CODE', 'English sentence.', status)`, add `codes.MY_CODE` to `errors.json` in `en` and `es`, run `npx vitest run tests/error-codes.test.ts`.

## 5. Add a language

Example: French (`fr`). Replace the code and names with yours.

1. Copy the English catalogs and translate the values only; keep keys and `{placeholders}`:
   ```sh
   cp -r src/i18n/messages/en src/i18n/messages/fr
   ```
2. Check the plural categories for the language (section 2) and give every plural object at least those forms, with `other` always present. The test fails on a missing category; it does not reject an extra one.
3. Register it in `LOCALE_DEFINITIONS` in `src/i18n/config.ts`:
   ```ts
   { code: 'fr', nativeName: 'Français', formatLocale: 'fr-FR' },
   ```
   `code` is the URL prefix, cookie value, folder name and `<html lang>`. The shipped codes are primary subtags (`en`, `es`) and a browser preference such as `fr-CA` still matches `fr`; put the region in `formatLocale`. `nativeName` is what the selector shows.
4. Enable it. Without this step it is registered but not offered:
   ```sh
   npm run configure -- --locales en,es,fr
   ```
   An unregistered code fails with the list of registered languages.
5. Optionally add a tagline. `description` may be a per-language map; a language without an entry falls back to the default language. `--description` only replaces the default language's entry, so edit the map in `src/template.config.ts` for the others.
6. Run `npm test`. `tests/i18n-messages.test.ts` fails with one line per problem: a missing folder or namespace file, a missing or extra key, a changed placeholder, plural text where English has plain text, missing plural categories, empty text, markup, stray braces, and a language used in `template.config.ts` that is not registered. `tests/i18n-translate.test.ts` and `tests/configure.test.ts` cover the translator and the CLI.
7. `tests/error-codes.test.ts` imports `en` and `es` explicitly. Add the new `errors.json` there too so its codes get the same checks (the parity test already compares its keys with English).
8. Check the language in the browser: unprefixed URLs with that `Accept-Language`, the selector, the cart, the admin, sign-in and consent. Automated tests cover catalogs and routing logic, not translation quality or layout.

Do not ship a language by copying English into the new folder and leaving it: the tests pass but the page is not translated.

## 6. What is not localized

- **Catalog data.** Product names, descriptions and categories are stored once, as the merchant entered them, and shown as entered in every language. The demo catalog is in English.
- **Brand name.** One string, `name`. Only the tagline (`description`) can be per language.
- **Notices.** The notice a merchant writes in runtime settings is shown as typed in every language ([runtime settings](runtime-settings.md)).
- **Email.** The template sends none. Any email you add needs its own localization.
- **Stripe.** The hosted Checkout line item is the fixed English text `Store order` (`src/payments/providers/stripe.ts`). The adapter passes no `locale` to Stripe, so what language the hosted page uses is Stripe's decision and has not been tested here.
- **Server text.** API messages, MCP, logs, telemetry, audit (section 4).
- **Right-to-left.** The root layout emits no `dir` attribute and the stylesheet was not reviewed for mirroring. Adding Arabic or Hebrew needs a CSS review first.
- **SEO.** No `hreflang`, sitemap or `robots` is generated. The page title comes from `common.meta.title` and the meta description from the `description` setting, both per language.

## 7. Currency

`currency` is the default (shipped `USD`); `currencies` is the list the product editor offers and must include it. Each code must be an upper-case ISO 4217 code that `Intl.supportedValuesOf('currency')` knows in the running Node; the list holds 1 to 30 codes without repeats.

```sh
npm run configure -- --currency EUR --currencies EUR,USD,GBP
npm run doctor
```

Without `--currencies`, the existing list is kept and the new default is added first when missing. You can also edit `currency` and `currencies` in `src/template.config.ts` directly; the app and `npm run doctor` apply the same validation. Rebuild or restart to apply it.

### What changes

- The currency preselected for a **new product** in the editor, and the order of the editor's list (default first).
- The currency of **empty totals**: the dashboard revenue card before any sale, and the cart's fallback currency when it holds no products.
- The currency shown as default in the admin settings panel.
- The demo catalog: `npm run demo:setup` seeds `templateConfig.currency`.

### What does not change

- **Existing prices.** Nothing is converted. A product keeps its own `priceMinor` and `currency`; the CLI prints that notice on every run. Reprice or recreate products if the amounts must change.
- **Per-product currency.** Each product has its own currency. A product whose currency is no longer in the list keeps it, and the editor still shows it. The list only limits the editor's dropdown: the domain, the HTTP API and the MCP tools accept any three upper-case letters as a product currency (`currency()` in `src/core/service.ts`), so it is not a server-side allowlist.
- **Mixed currencies.** An order must use one currency. The domain rejects a mix with `MIXED_CURRENCY` (422) and the cart detects it before submitting. A catalog in several currencies cannot be bought in a single cart.
- **Stripe.** Offering a currency does not make it payable. The hosted Checkout adapter accepts only the codes in `STRIPE_CURRENCY_EXPONENTS` whose exponent matches `Intl`, and rejects the rest with `PAYMENT_CURRENCY_UNSUPPORTED` before stock is reserved ([payments](payments.md)). Manual orders have no such limit.

### Minor units

Money is an integer in the currency's minor unit. The factor comes from `Intl` (`currencyFactor` in `src/i18n/format.ts`): `USD` 100, `PYG` and `JPY` 1, `KWD` 1000. The editor converts what the person types with `Math.round(price * factor)`; display divides by the same factor. Prices are always resolved on the server; the browser total is only a confirmation.

The demo seed (`demoCatalog` in `src/db/seed.ts`) writes prices as major-unit numbers and multiplies by the factor, so `USD` 29 is 2900 and `KWD` 29 is 29000. For zero-decimal currencies the same numbers become small amounts (29 `JPY`, decimals rounded): the demo shows the mechanism, it is not a realistic price list. `tests/seed-currency.test.ts` covers `EUR`, `GBP`, `JPY` and `KWD`. `seedDemo` never rewrites an existing product, so an older `demo.db` keeps its old names and currency; `demo:setup` warns about that and the fix is to delete `demo.db` and rerun.

### Formatting by language

`formatMoney`, `formatNumber` and `formatDateTime` use the language's `formatLocale`, so one price formats differently per language. Sample output of Node 22 with its bundled ICU data (browsers may differ slightly):

| Amount | `en-US` | `es-PY` |
| --- | --- | --- |
| 2900 USD | `$29.00` | `USD 29,00` |
| 123450 EUR | `€1,234.50` | `EUR 1.234,50` |
| 32000 PYG | `PYG 32,000` | `Gs. 32.000` |

Changing the language never converts or reprices anything.

npx vitest run tests/i18n-messages.test.ts tests/i18n-routing.test.ts tests/i18n-translate.test.ts tests/error-codes.test.ts tests/configure.test.ts tests/seed-currency.test.ts
